MCP 是什么

MCP(Model Context Protocol,模型上下文协议)是 Anthropic 于 2024 年底开源的一项协议，现已成为 AI 应用连接外部工具与数据的事实标准。简单来说,它定义了一套统一的接口规范,让 LLM 应用能够以标准化的方式访问文件系统、数据库、API、Web 服务等外部资源。

在没有 MCP 之前,每个 AI 应用接入每种工具都需要单独编写适配代码,存在典型的"M×N 集成问题":

  • M 个 AI 应用 × N 种工具 = M×N 份集成代码
  • 每新增一个应用或工具,集成本就翻倍增长

引入 MCP 后,架构从"多对多"退化为"多对一":

  • M 个 AI 应用 + N 种工具 = 开发 M+N 个符合 MCP 的实现即可

这和 USB-C 接口的理念非常相似:过去每种设备各有各的充电口,统一之后,一个接口连接所有设备。

  • Host:运行 AI 应用的一方(如 OpenCode、Claude Desktop、各类 IDE 插件)
  • Client:Host 内部的连接器,每个 Client 与一个 Server 保持 1:1 会话
  • Server:轻量级服务进程,向 AI 暴露某种具体能力,例如操作 Git、查询 PostgreSQL、抓取网页

三大原语

MCP Server 可以向 Host 暴露三类能力,称为"原语"(primitives):

原语方向说明典型例子
Tools模型可控由 LLM 决定何时调用,类似函数调用执行 SQL、创建 Issue
Resources应用可控由 Host/用户决定何时读取的上下文数据代码文件、数据库模式
Prompts用户可控由用户主动触发的预制提示词模板“/review” 发起代码评审

把 Tools 理解为"AI 能做什么",Resources 理解为"AI 能看到什么",Prompts 理解为"AI 能被指示怎么做",这个协议一下子就好记了。

💡 另外还有 Sampling(服务端反向请求 LLM 补全)和 Roots(限定可访问目录)等高级能力,初学阶段可以暂不关注。

传输方式

Client 与 Server 之间的通信支持两种标准传输:

传输适用场景说明
stdio本地部署Server 作为子进程启动,通过标准输入/输出通信,实现最简单,适合本地工具
Streamable HTTP远程/共享服务基于 HTTP + SSE 的双向流式通信,适合团队共享的远程 MCP 服务

本地个人使用选 stdio 即可;想让团队所有人共用同一个 MCP 服务(比如内部知识库),就走 Streamable HTTP。

快速上手:写一个最小的 MCP Server

以官方 Python SDK 为例,10 行核心代码就能对外暴露一个工具:

1

pip install "mcp[cli]"

创建 server.py:

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("my-first-server")

@mcp.tool()
def add(a: int, b: int) -> int:
    """两数相加"""
    return a + b

if __name__ == "__main__":
    mcp.run()  # 默认以 stdio 传输运行

运行验证:

1

mcp dev server.py   # 启动官方 Inspector 调试界面

浏览器会打开 Inspector,可以看到刚才注册的 add 工具,并直接调用测试。所有带类型签名的函数、docstring 都会自动转换成符合规范的 Tool 定义——Type hints 就是文档,这是 Python SDK 最大的优点。

TypeScript 生态同样成熟:

1

npm install @modelcontextprotocol/sdk

在 OpenCode 中使用 MCP

关于 OpenCode 本身,可以参考我之前的文章《OpenCode —— 开源 AI Coding Agent 介绍与操作指南》。

OpenCode 原生支持 MCP,一条命令即可接入.stdio 方式:

1

opencode mcp add github -- claude mcp run @modelcontextprotocol/server-github

远程 HTTP 方式:

1

opencode mcp add --transport http docs https://docs.example.com/mcp

配置保存在项目的 opencode.json 中,可以随项目提交,团队成员拉取后即获得相同的工具集。

常见 MCP 服务器生态

经过两年多的发展,MCP 已经积累了相当成熟的生态,官方维护的就有一批高可用 Server:

Server能力适合谁
Filesystem受控的本地文件读写所有人
GitHubIssue/PR/仓库管理团队与开源维护者
Playwright浏览器自动化与 E2E 测试测试工程师
PostgreSQL / SQLite只读 SQL 查询数据分析
Fetch网抓内容转 Markdown所有需要联网资料的场景
Slack消息检索与发送办公协作

在 MCP Servers 目录 和 mcp.so 可以找到更多社区实现的 Server。

安全与实践建议

把工具交到 AI 手上,安全性必须放在首位:

  1. 最小权限原则 — 如 Filesystem Server 支持指定允许访问的目录白名单,不要把整个磁盘交给 AI
  2. 慎用凭证 — GitHub 等需要 Token 的 Server,用最小 scope 的 PAT,并按需设置只读
  3. 警惕提示注入 — AI 可能读取到恶意网页内容后调用你的本地工具,敏感操作(删除、付款等)工具设计上要加确认门槛
  4. 供应链审查 — 第三方 MCP Server 部署前审查其源码或发布来源,优先选择官方与高星数实现
  5. 企业内部用只读(Server)起步 — 团队落地 MCP 的稳妥路径:先做到"AI 只能读",验证价值后再逐步开放写能力

小结

  • MCP 用统一的协议标准把 AI 应用 ↔ 工具 的集成从 M×N 降到 M+N
  • 三大原语:Tools(AI 能做)、Resources(AI 能看)、Prompts(AI 能被指点)
  • 本地 stdio、远程 Streamable HTTP 两种传输,按场景选型
  • OpenCode 等主流 AI 编程工具已原生支持,一条命令接入即可

工具生态的标准化,正在让"AI 会用工具"从演示变成生产力。如果你也用 AI 辅助开发,值得花半小时动手把 MCP 跑起来。
