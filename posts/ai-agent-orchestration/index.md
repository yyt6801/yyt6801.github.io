# AI Agent 编排：从 SpaceX AI 到 Michelin 厨房的实践


## 引言：从“软件工厂”到“Michelin 厨房”

在 2026 年，SpaceX AI 的首席工程师 Lauren Tan（X 账号 @poteto）揭示了她团队如何在短短一个月内合并 **2,500 个 PR 到生产环境**。她明确表示，这一数字的背后并非魔法，而是两件大多数团队会忽略的事情：

1. **构建 Agent 工作的环境**
2. **提供验证机制，让 Agent 能检查自己的工作**

她将流行的“软件工厂”比喻重新定义为 **Michelin 厨房**——因为工厂式生产不具备“工匠精神”和品质保证。正如她所说：

&gt; “我希望能够同时实现**品质**与**规模**——这正是米其林厨房的核心理念。”

---

## Lauren Tan 与 SpaceX AI 的 Agent 编排体系

### 三层架构：协调、执行、编排

Tan 在多场工作坊和直播中阐述，她将 Agent 组织为三个层级：

| 层级 | 名称 | 职责 | 典型规模 |
|------|------|------|----------|
| **第一层** | **协调层** | Chief of Staff 编写不写码，只负责解释任务、拆解工作、分配角色、跟踪进度 | 超过 10 个编排器同时运行 |
| **第二层** | **执行层** | 运行 10-20&#43; 个 Grok Bot 并行代理，覆盖移动端、桌面端、基础设施、测试框架 | 并发执行规模 |
| **第三层** | **编排层** | `/poteto-mode` 入口，根据任务类型选择 Playbook，调用 `/loop`、`/goal`、`/swarm`、`/arena`、`/interrogate` 等命令 | 任务驱动型 |

&gt; **关键洞察**：协调层的 Agent **不编写代码**，只负责解释任务和分配。执行层则是大规模并行的 Agent 池。编排层则负责根据任务类型动态选择策略。

### 编排命令体系

Tan 开源的 **pstack** 工具提供了丰富的编排命令：

| 命令 | 说明 | 典型用例 |
|------|------|----------|
| `/loop` | 迭代循环 | 持续改进、重构 |
| `/goal` | 长期目标 | 大型项目拆解 |
| `/swarm` | 并行分片 | 大任务并行拆解 |
| `/arena` | 竞争性解 | 多 Agent 竞争最佳方案 |
| `/interrogate` | 跨模型审查 | 不同模型相互审查工作 |

&gt; **任务类型固定流程**：
&gt; - Bug 修复：先复现问题 → 找根 cause → 验证修复 → 自动合并
&gt; - 重构：记录当前行为 → 证明行为不变 → 进行重构 → 验证

## 核心原则：三大支柱

### 1. 验证是核心技能

Tan 明确指出，她之所以能信任 Agent，并非因为模型变聪明，而是因为**验证和工程防护层变强**。

&gt; “单最重要的技能应该在你工具箱里的是**验证**。”

**验证的三要素**：
- **给 Agent “手和眼睛”**：Agent 能够运行代码，交互式调试，取 traces 和 snapshots
- **循环的关键**：验证是循环中最重要的部分，因为 Agent 能自行检查工作，将人从方程中移出
- **自动化基础设施**：Cursor 和 xAI 的每个应用都有内置的、自动维护的验证技能，已成为团队的关键基础设施

**验证能力的具体表现**：
- Chrome DevTools Protocol（控制浏览器、截图、点击元素、读取控制台日志）
- 移动端模拟器通过用户流驱动
- 代码运行与调试
- CI/CD 集成的回归测试

### 2. 两层循环架构

Tan 运行两个相互关联的循环：

| 内层循环 | 外层循环 |
|----------|----------|
| Agent 工程师在代码中工作，朝着**意图的快照**努力 | 代码库之外的一切：Slack、Linear、X 上的 Bug 报告 |
| 快照可能会过期，需要人作代理 | 新信息出现，需要人充当代理 |

**具体布线示例**：
- **Slack MCP** 或订阅单一频道：Bot 监听，Bug 报告时自动复现问题，用验证技能确认 Bug 在 main 上仍存在，将其放入 Cursor 项目
- “Cursor 项目是我的内层循环，Grok Bot 是我的外层循环。”

### 3. 缓冲而非逐一修复

&gt; “我并不告诉它先修复每个 React 脚手架陷阱。我让它将其追加到一个文档中，每隔 couple 天我查看一下，发现它们都是同一类问题。”

**为什么要用缓冲？**
- 纯执行模式下，有时会错失大局
- 缓冲强制 Agent（和自己）思考大局
- 给 Agent 和自己提供识别可能错过的模式的方式

### 4. 一次性门 vs 两次性门

Tan 强调区分两类 PR：

| 两次性门 | 一次性门 |
|----------|----------|
| 可 merge 并 revert（廉价回退） | 会导致数据丢失或不可逆操作 |
| 安全不敏感领域 | 医疗、法律、金融等敏感领域 |

**关键判断**：
- 关于是否可验证程序化决定
- 对数学、证明等领域是可验证的
- 软件和数学部分是可验证的

&gt; “如果大多数 PR 都是一次性门，我无自动合并的答案。人仍需在敏感领域签 off。”

## 实际编排实践指南

### 1. 从本地开始，再扩大规模

&gt; “Tan 推荐在局部运行工作流后，再扩展到云端代理。”

**建议路径**：
1. 本地验证工作流运行正确
2. 任务必须具备可验证性（可通过代码验证）
3. 变更必须可逆（或有回滚机制）
4. 再逐步引入云端 Agent

### 2. 技能 = 过程转化为文字

Tan 同意“skill（技能）= 过程转化为文字”。随着模型改进，技能会**收缩**（即表述更简洁，但涵盖更广）。

**技能构建建议**：
- 将具体的业务过程提炼为清晰的文字描述
- 包含前置条件、执行步骤、验证标准
- 作为 Agent 的系统提示词一部分

### 3. 协调 Agent 不做单独工作

&gt; “Cursor 的 projects 特性是‘协调 Agent’，它有自己的‘计算机’，是经理/主厨。它不自己做工作，而是分配和协调。”

**反模式**：
- 每个任务 spawn 一个 Agent（“一人一任务”）会导致线程断裂
- 可能重复工作，或错过高层级问题

**推荐模式**：
- **多个 Bug 报告**让协调 Agent “zoom out”，发现真正的 Bug 在别处
- 协调 Agent 分配给子 Agent，保持工作连贯性

### 4. 模型路由与任务匹配

Tan 提到，根据任务类型调整模型和推理级别：

- **straightforward tasks**：更快的模型，较低的推理级别
- **需要规划和推理的任务**：更强的模型，较高的推理级别
- **云代理**提供细粒度控制，可根据任务类型切换模型

### 5. 环境优化优于 Agent 优化

&gt; “审视 Pull Request 中的低效模式和坏习惯，思考如何修正**环境**，而非单个 Agent。”

**环境修正的例子**：
- 技能（Skills）
- 约束（Constraints）
- Lint 规则
- 类型系统

&gt; “如果是一时的偶发问题，无妨。如果多个 Agent 有相同的问题、同样的捷径、同样的变通方法——那是修正‘厨房’（技能、约束、Lint、类型系统）的信号。”

## 总结与展望

Lauren Tan 在 SpaceX AI 的实践为 AI Agent 编排提供了宝贵的经验：

### 关键取得：
1. **验证是基础**：没有强大的验证机制，大规模 Agent 编排就是灾难
2. **两层循环**：内层关注代码意图，外层关注代码库之外的上下文
3. **Michelin 厨房思维**：在规模中保持品质，而非纯粹的 mass production
4. **环境优先**：通过优化技能、约束和系统来修正环境，而非不断微调 Agent
5. **一次性门/两次性门**：基于验证质量判断哪些可以自动合并

### 经典语录：
&gt; “The 2,500 PRs are not 2,500 features. A lot of the work is spent on gardening.”—— Lauren Tan

&gt; “It all comes back to the quality of the verification you can get out of your agent.”—— Lauren Tan

### 实施路线图：

| 步骤 | 描述 |
|------|------|
| **第一步** | 构建验证能力：给 Agent “手和眼睛”，确保能运行代码和交互 |
| **第二步** | 搭建两层循环：内层关注代码意图，外层收集外部上下文 |
| **第三步** | 实施三层编排：协调层→执行层→编排层 |
| **第四步** | 建立缓冲机制：用文档/队列收集模式，而非逐一修复 |
| **第五步** | 定义一/二次性门：基于验证质量判断自动合并边界 |
